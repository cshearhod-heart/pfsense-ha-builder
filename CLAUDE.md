# pfSense HA / CARP Builder — Claude Code Project

Standalone tool project. Generates paired primary/secondary pfSense configs for CARP HA from a config.xml backup. No customer data lives here and none should be added — this repo is pure tooling.

## Files

```
pfsense-ha-builder.html   # Standalone browser tool. SOURCE OF TRUTH. Single self-contained file.
test-fixtures/            # Synthetic config.xml only — never a real backup.
```

## Domain facts worth not re-deriving

Verified directly against pfSense's own PHP source (github.com/pfsense/pfsense, `src/usr/local/www/` and `src/etc/rc.filter_synchronize`) rather than assumed from memory — these are load-bearing for correctness:

- **`hasync` is a top-level config.xml element**, not nested under `<system>`. Fields: `pfsyncenabled`, `pfsyncinterface`, `pfsyncpeerip`, `synchronizetoip`, `username`, `password`, plus ~20 boolean `synchronize*` section flags (see `system_hasync.php`).
- **CARP VIPs** live at `virtualip/vip` with `mode=carp`: `interface`, `type`, `subnet`, `subnet_bits`, `vhid`, `advbase`, `advskew`, `password`, `descr`, `uniqid` (see `firewall_virtual_ip_edit.php`).
- **The primary's own XMLRPC config-sync engine adds +100 to `advskew`** (capped 254) when pushing a CARP VIP to the secondary, and **rewrites `dhcpd/<iface>/failover_peerip` to the sender's own interface IP** on every sync (see `rc.filter_synchronize`, functions `backup_vip_config_section()` and the dhcpd loop in `carp_sync_xml()`). The generator bakes in these post-sync values directly so both files are correct from first boot, not just after the first sync fires.
- **Config sync is one-directional.** `synchronizetoip` should be set on the primary only; setting it on the secondary risks a sync loop/conflict. The secondary's copy is left blank.
- **DHCP backend is `dhcpbackend`** (top-level, `isc` or `kea`, default `isc` — see `pfsense-utils.inc`, `dhcp_get_backend()`). Kea's HA is a different mechanism (hot-standby, mTLS peering) and is genuinely not compatible with the ISC `failover_peerip` approach — confirmed independently by Heart's own `~/second-brain/team/pfsense-configuration-standard.md`, Section 3. Never synthesize Kea HA config from assumption; it's flagged out of scope in the UI instead.
- **Interface `gateway` is a name reference** (into `gateways/gateway_item`), not a literal IP — the secondary keeps the same gateway reference, since it shares the same upstream gateway; only `ipaddr` changes.
- **`hasync/password` is not an independent secret** — traced through `xmlrpc_client.inc` (sender) and `xmlrpc.php` (receiver, `authenticate_user()`): the primary sends `hasync/username`/`hasync/password` as literal HTTP Basic Auth to the peer, validated the same way as a WebGUI login. It must be the account's *actual* current password, not an arbitrary new value — found this the hard way reviewing real output, not from source-reading alone.
- **ISC DHCP failover has a startup fail-safe, confirmed against Netgate's own troubleshooting doc**: a server that can't reach its failover peer at startup intentionally stops issuing *new* leases (not a config bug, and CARP/pfsync are unaffected). Found this from a real user report — DHCP stopped on the primary after importing it alone, with the secondary not yet online. The tool now warns about this in both the DHCP-failover form section and the final output panel.
- **CARP password is silently truncated past 19 characters.** Confirmed in FreeBSD source (not pfSense's own): `sbin/ifconfig/carp.c` does `strlcpy(carpr.carpr_key, carpr_key, CARP_KEY_LEN)`, and `CARP_KEY_LEN` is 20 (`sys/netinet/ip_carp.h`) — no error, no warning, just a quietly shorter effective password. pfSense's own PHP layer (`interfaces.inc`) also strips all spaces from the password before applying it via `ifconfig`. The generated random password is kept to 16 characters and space-free for exactly this reason.

## Kea HA

Verified against pfSense's Kea settings page (`services_dhcp_settings.php`) and a real customer's working Kea HA config (their pilot, via Frank) — not guessed:

- **`<kea><ha>` fields**: `enable`, `role` (`primary`|`standby` — not "secondary"), `localname`, `localip`, `localport`, `remotename`, `remoteip`, `remoteport`, `heartbeatdelay`, `maxresponsedelay`, `maxackdelay`, `maxunackedclients`, `maxrejectedleaseupdates`, `tls`, `scertref`, `mutualtls`, `ccertref`.
- **It rides the same dedicated SYNC link as pfsync** — confirmed directly from the real reference config, where `kea/ha/remoteip` was identical to `hasync/pfsyncpeerip`. This isn't a coincidence to route around; it's the natural pattern, and the generator reuses `s.syncIpPrimary`/`s.syncIpSecondary` for Kea's `localip`/`remoteip` rather than inventing a separate address scheme.
- **pfSense's own sync engine's transform** (`rc.filter_synchronize`, the `foreach (['kea','kea6'] as $kea)` block) is the exact spec to mirror: swap `localip`↔`remoteip` and `localport`↔`remoteport`, flip `role` (primary↔standby), set the new box's `remotename` to the old box's `localname` — and `localname`/`tls`/`mutualtls`/`scertref`/`ccertref` are deleted from what gets pushed (i.e., never carried over automatically; the secondary needs its own `localname`, which the generator sets from `secHostname`). The five delay/limit tuning fields are untouched by that transform, meaning they're **not** in the swap or delete lists — carry them through unchanged when adopting an existing config.
- **TLS/mutualTLS detection must not under-detect.** pfSense's boolean convention is genuinely inconsistent between fields (some empty-tag-presence, some literal text `"on"`) and no real example with TLS enabled was available to confirm which `ha/tls` uses — so it checks both conventions rather than assume. Getting this wrong in the "doesn't detect TLS" direction would mean silently generating a secondary with real cert reference IDs that don't apply to it.
- **Kea HA is a separate concern from CARP/hasync**, not a replacement — a config can (and typically will) have existing CARP + hasync + Kea HA all at once, all riding the same SYNC interface. Test fixture `sample-config-kea-existing-ha.xml` covers exactly this combination.

## Existing-HA mode

If the primary already has a CARP VIP on an interface, or `hasync` already points at a live (non-spare) pfsync interface, that interface/section switches into "adopt as-is" mode — the whole point is a secondary generated to match, never re-deriving or touching what's already live on the primary. Real gotchas hit building this, worth not re-deriving:

- **A live sync interface has a static IP, so it's `isStatic` too** — meaning every place that filters interfaces by `isStatic` for CARP-candidate purposes must *also* exclude whichever key `hasync/pfsyncinterface` names (`activeSyncKey()`), or the sync interface shows up as a bogus CARP card of its own. Two separate call sites had this copy-pasted inconsistently during development (one updated, one missed) — that's exactly why it's now a single shared helper instead of an inlined check in each spot.
- **Both generated docs start as clones of the same original**, so an existing `<vip>` is already present in *both* before any mutation — not just the primary. Appending a new element for the secondary's "matching" VIP produced a duplicate (the original one plus a freshly appended one) until the fix: for existing rows, find the existing element by interface key and update its `advskew` in place, exactly like pfSense's own sync engine does (which also means the secondary's `uniqid` ends up identical to the primary's for an adopted VIP — correct, not a bug, since real pfSense sync never regenerates it either).
- **Distinguish "reusing a spare interface" from "the sync interface is already fully live."** Both end up with `s.syncSource` set to some interface key, but only the spare case should have the primary's `if`/`ipaddr`/`subnet`/`descr` written at all — an already-live sync interface must not be touched even to re-write the same value it already holds. Compute `existingSyncActive` once per generation and thread it through explicitly; don't try to infer it from `syncSource` alone.

## Stale messaging left behind when Kea HA support was added

`renderAnalysis` (the "What we found" panel, step 2) had its own `a.backend === 'kea'` callout saying Kea HA "will be skipped... configure manually" — written before Kea HA support existed, and never updated when it was added, because that work touched `renderDhcpSection` (step 4) and the stale copy lived in a different function entirely. It sat there contradicting the correct step-4 behavior until a user's confusion led back to it. When a capability changes behavior for a backend/mode, grep for *every* message mentioning that backend/mode across the whole file, not just the section being actively edited — `renderAnalysis` and `renderDhcpSection` both editorialize about the same `a.backend === 'kea'` condition independently, and there's no single source of truth for that copy.

## "Primary unchanged" detection, and a Document.cloneNode gotcha

When everything selected is adopt-as-is (existing VIPs, existing SYNC/hasync, existing Kea HA), the generated primary can be — and with a real fully-HA'd customer config, was — functionally identical to the upload except for the always-bumped revision block. `generateConfigs()` detects this (`primaryUnchanged`) and the output panel relabels the download card accordingly, rather than leaving the user to wonder whether there's something to import (this exact confusion happened before the detection existed).

**Don't compare via `primaryDoc.cloneNode(true)`.** Cloning a `Document` doesn't reliably preserve whatever internal state `XMLSerializer` uses to decide whether to emit the `<?xml version="1.0"?>` declaration — the clone silently serialized without one, while the real (non-cloned) `primaryDoc` correctly had it, breaking the comparison while leaving the actual generated output fine. Fixed by serializing `primaryDoc` once (the real output) and re-parsing *that string* for the stripped-revision comparison, instead of cloning the Document. Found by testing against a real config, not by inspection — the bug was silent (no thrown error, just a wrong boolean).

## Another real bug found in existing-HA testing

`suggestRealIps()` only ever excluded the interface's own current address and the DHCP pool — fine for fresh-build "reuse" mode, where the VIP-to-be *is* that current address anyway. But for an existing-VIP row, the VIP is a *separate* address (the split into real IP + VIP already happened previously), so the suggestion could land squarely on the VIP itself. Fixed by adding an optional `extraExclude` list to `suggestRealIps()` and passing `[existingVip.subnet]` for existing-VIP rows. Any future caller suggesting an address near an already-established VIP needs to pass that exclusion too — it's not automatic.

## Known gap, not yet built

Repurposing an interface (e.g. an old GUEST slot manually moved to a VLAN, freeing the physical port for SYNC) can leave stale `<filter><rule>` entries still targeting the old interface key — found in real output review: rules meant for GUEST were still active on `opt1` after `opt1` became the dedicated SYNC interface, effectively giving the SYNC link a "pass any outbound" rule nobody intended. This tool doesn't scan or flag filter rules at all currently. Worth adding: cross-reference `filter/rule/interface` against the interfaces selected for CARP/SYNC and flag any rule targeting an interface whose *role* changed, without auto-deleting anything (a firewall rule change should always be a reviewed, deliberate action).

## Invariants to preserve

1. **Fully offline, single distributable file.** No network calls, no server dependency. A pfSense backup can contain the admin password hash, CARP secrets, and VPN private keys — nothing should ever leave the browser tab.
2. **Parser is schema-tolerant, not version-branching.** It only reads/writes the specific tags above and clones everything else in the source config verbatim. Don't add pfSense-version-specific branches without verifying against source first — the whole point of the tolerant design is to survive schema drift across CE/Plus releases without silently corrupting unrelated sections.
3. **Never guess an XML tag name from memory alone.** Every field this tool writes was checked against pfSense's own PHP source. If a new field needs adding, verify it the same way (`curl raw.githubusercontent.com/pfsense/pfsense/master/src/...`) before writing generator code — a wrong tag name is a config that silently doesn't work on a real firewall.
4. **Out-of-scope sections (IPsec, OpenVPN, certs, Kea HA) are flagged, never silently modified or silently dropped.**
5. **SYNC interface source is a choice, not a fixed behavior**: create new, or reuse an existing interface slot that's present in the config but unused (no `<ipaddr>`, not `<enable>`d). This was added after a real test run — a lab unit had no spare physical NIC, and the fix was moving another interface onto a VLAN first (outside this tool) to free up a slot, then reusing that slot here. On reuse, never touch the primary's `<if>` — it's already real hardware in the source config.
6. **VLAN pseudo-interfaces are locked, not editable**, in the "secondary physical port" field. `<if>` for a VLAN interface is a computed value (parent port + tag from the top-level `<vlans>` section), not a free-form NIC name — editing it without also fixing the matching `<vlans>` entry produces a dangling reference. Detected by matching each interface's `physIf` against `vlans/vlan/vlanif`.
7. **Per-interface VIP strategy defaults to "current IP becomes the VIP," not "keep current IP, VIP is new."** CARP only protects an address that something downstream actually points at — if the primary keeps its current IP, nothing is protected unless every downstream device is repointed at the new VIP, which this tool can't do. Reusing the current IP needs zero downstream changes, which is why it's the default. This also means the primary's own `<ipaddr>` is no longer untouched in the generator — it changes too, in "reuse" mode.
8. **DHCP's `gateway` override is not optional when "reuse" mode applies to a DHCP-enabled interface.** Verified in `services.inc`: pfSense falls back to the interface's own IP for the DHCP-issued default gateway when `dhcpd/<iface>/gateway` is empty. After a "reuse" swap that fallback is the new non-floating address, so the override must be set explicitly to the VIP — this isn't a preference toggle, the alternative is just wrong.
9. **Output gets a whitespace-only reindent pass (`reindentXml`) before serialization**, since DOM `appendChild` doesn't insert the surrounding indentation a hand-edited file would have — newly appended elements landed crammed on one line otherwise (found reviewing real output against the original). The pass only ever touches pure-whitespace text nodes between element children; if a container has any non-whitespace, non-element child it's left alone entirely, so it can never silently drop something unexpected. Separately, XMLSerializer always normalizes `<tag></tag>` to `<tag/>` document-wide — that's an unavoidable, harmless side effect of the DOMParser/XMLSerializer round-trip (pfSense's parser treats them identically), not something to try to "fix."
10. **A physical port is "claimed" the moment any interface entry declares it in `<if>`, regardless of whether that interface is actually configured.** pfSense's own interface-assignment page won't let two logical interfaces share one physical port even if one of them has no address or is disabled — so `usedPhysIfs` (the SYNC "create new" collision check) must stay strict and count spare/unconfigured slots too. Don't relax this to "only count configured interfaces" — that was tried and reverted after producing a config with the same physical port assigned to two interface entries. The "reuse existing" SYNC source is the correct path for a spare-but-defined slot; the fix for a confusing block there is a clearer error message pointing at that path, not loosening the check.
11. **SYNC link subnet is base-address + mask-dropdown, not a typed CIDR string.** A single combined text field was more fragile than it needed to be for a fixed, well-known value set. `/31` is a supported mask and gets RFC 3021 handling (`linkHosts()`): no network/broadcast reserved, both addresses in the pair are host-usable — for bits 8-30 the two hosts are network+1/network+2 as before, for bits===31 they're network/network+1.
12. **Never fetch "entropy" (or anything else) from a network source, even when asked.** A request came in to pull randomness from an external site; the right call was to explain why `crypto.getRandomValues()` is already a proper local CSPRNG (not weaker than a remote string) and that fetching one would break invariant #1 for a tool whose whole point is that a pfSense backup's secrets never leave the browser. Generate randomness locally, always.

## Testing gotcha: browser caching of the local test server

Navigating the Browser pane back to the same `http://localhost:PORT/pfsense-ha-builder.html` URL after editing the file does not reliably pick up the change — the browser can keep serving a cached copy of the script, silently testing stale code while every request/response looks normal. Symptom: a function behaves like an older version, or a feature that was just added appears entirely absent, with no error. Append a cache-busting query string (`?cb=<anything>`) on every re-navigate during iterative testing, or the "browser vs. real bug" confusion this caused once will happen again.
